# API contracts (as implemented, M4)

Base path `/api/v1`. The OpenAPI schema is generated by FastAPI at `/openapi.json`, with an interactive view at `/docs`.

## Errors
Every error response has the same shape: `{"error": {"code": str, "message": str, "details": any|null}}`. Stack traces are never returned.

Common codes:
- `validation_error` (422)
- `not_found` / `<resource>_not_found` (404)
- `invalid_config`, `config_exceeds_limits`, `scenario_too_large`, `invalid_scenario`, `invalid_graph` (422)
- `idempotency_conflict`, `scenario_in_use` (409)
- `queue_full` (429)
- `database_not_configured` (503)
- `internal_error` (500)

## Health and metadata
- `GET /health`: liveness. Reports database status as `ok`, `unavailable` or `not_configured`.
- `GET /ready`: readiness. 200 only if the database is reachable, else 503.
- `GET /algorithms`: id, version, `uses_seed` and default config for each algorithm.
- `GET /meta`: app version and request limits. Contains no secrets and no URLs.

## Built-in scenarios (no database)
- `GET /scenarios/builtin`
- `GET /scenarios/builtin/{id}`
- `POST /routing/shortest-path`

## Scenarios and immutable versions
- `GET /scenarios?limit&offset`
- `POST /scenarios` with `{name, description, data | builtin_id}`. Returns 201 and creates version 1.
- `GET /scenarios/{id}`: the scenario with its version list.
- `PATCH /scenarios/{id}`: `name` and `description` only.
- `DELETE /scenarios/{id}`: 204. Returns 409 `scenario_in_use` if any run or suite references any of its versions.
- `POST /scenarios/{id}/versions` with `{data, note}`. Returns 201 with the next `version_number`, which becomes the current version.
- `GET /scenarios/{id}/versions/{number}` and `GET /scenario-versions/{version_id}`.

Versions are never updated. A Postgres trigger rejects `UPDATE` on `scenario_versions`. Each version stores a SHA-256 fingerprint of its canonical content.

Submitted data is validated in this order: limits, then structure (`GraphError`), then `validate_scenario` errors. Capacity infeasibility is allowed at this stage and reported by the algorithms.

## Runs
- `POST /runs` with `{scenario_version_id, algorithm_id, config, seed?, idempotency_key?}` (or an `Idempotency-Key` header). Returns **202** and a `Location` header.
  - The config is resolved and validated, then checked against server limits.
  - For seeded algorithms a missing seed is generated and stored **before** execution.
  - The run row is inserted as `QUEUED` and committed before the response.
- **Idempotency:** the same key with the same body returns the original run with 200. The same key with a different body returns 409. Concurrent duplicates are resolved by the unique key.
- `GET /runs?status&algorithm_id&scenario_version_id&suite_id&limit&offset`
- `GET /runs/{id}`: returns `status`, `attempt`, timestamps, the latest `progress` summary, `termination_reason` and `error`.
- `POST /runs/{id}/cancel`: idempotent.
  - `QUEUED` becomes `CANCELLED` immediately (202).
  - `RUNNING` becomes `CANCELLING` (202); the worker stops cooperatively within about one heartbeat interval.
  - Terminal or `CANCELLING` runs are unchanged (200).
- `GET /runs/{id}/result`: 404 `result_not_available` until there is a result. A cancelled run that had started keeps its best-so-far result, with `termination_reason: cancelled`.
- `GET /runs/{id}/events`: Server-Sent Events.
  - Each event is `id: <event id>`, `event: <type>`, `data: {id, kind, type, payload, created_at}`.
  - Lifecycle types: `queued`, `started`, `cancel_requested`, `requeued`, `completed`, `cancelled`, `failed`.
  - `progress` events carry iteration, evaluations, elapsed_s, best_objective, current_objective, has_feasible and message. There is no percentage field.
  - Resume with `Last-Event-ID` or `?after=`.
  - The stream ends with `event: end` once the run is terminal and drained, or with `event: timeout` after `sse_max_duration_s`, after which the client should reconnect.

### Lifecycle
```
QUEUED -> RUNNING -> COMPLETED
   |         |  \-> FAILED            (algorithm exception, or worker lost with no attempts left)
   |         \-> CANCELLING -> CANCELLED
   \-> CANCELLED
RUNNING --(stale heartbeat, attempts left)--> QUEUED   (bounded retry)
```
- Every transition is a conditional `UPDATE ... WHERE status IN (...)`. Terminal states never change.
- A run that receives a cancel request ends `CANCELLED`, even if its algorithm then finishes normally.
- Only the worker that owns a run (`worker_id`) can heartbeat, report progress, complete or fail it.

### Retry semantics
- **Algorithm exceptions** → `FAILED` with `error = {code: algorithm_error, type, message}`. They are not retried, because they are deterministic for a given input.
- **Worker interruption** (no heartbeat for `stale_after_s`):
  - `CANCELLING` → `CANCELLED`;
  - otherwise re-queued while `attempt < max_attempts` (default 2);
  - otherwise `FAILED` with `worker_lost`.
- **Delivery is at least once.** A stalled but alive worker may still be executing a run that has already been re-queued. Its later writes are rejected (it no longer owns the run), and `run_results` has one row per run, so only one result is stored. Exactly-once execution is **not** claimed.

### Bounded event volume
- Progress events are throttled (`progress_event_min_interval_s`) and capped per run (`max_progress_events_per_run`). The latest summary is always in `optimization_runs.progress`.
- Progress events of finished runs older than `event_retention_days` are pruned by the worker. Lifecycle events are kept.

## Benchmark suites
- `POST /suites` with `{name, scenario_version_id, specs: [{algorithm_id, config, label?}], seeds | repetitions, budget_policy}`. Returns 202.
  - Creates the suite and all specs × seeds runs in **one transaction**, as ordinary queued runs.
  - Seedless algorithms are simply repeated, with seed `null`.
- `GET /suites`, `GET /suites/{id}`: the suite with run ids and status counts.
- `GET /suites/{id}/comparison`: summaries (n, feasible rate, mean, median, std, best, worst, wall time, gap) and a labelled gap reference.
  - Built from **stored** results of **COMPLETED** runs only. Cancelled, failed and unfinished runs are counted per spec and never imputed. `complete` tells whether every run has finished.
- `GET /suites/{id}/export?format=json|csv`: the same data, plus per-run rows and reproducibility metadata (scenario fingerprint, seeds, specs, budget policy, evaluator and software versions recorded by the worker).
